# 화면 코드 정리·테스트·공통코드화 설계 (2단계)

작성일: 2026-11-22

## 1. 왜 하는가

1단계에서 서버 코드는 기능별 구조와 촘촘한 테스트를 갖췄지만, 화면 코드(`src/public/`)는 그대로입니다. 남은 문제는 세 가지입니다.

- **덕지덕지 붙은 구조:** `server-detail.js`(1,608줄, 모듈 전역 변수 19개), `report-detail.js`(992줄)처럼 큰 파일에 DOM 조작·상태·API 호출이 섞여 있습니다.
- **테스트가 없습니다:** 페이지 파일은 불러오는 순간 DOM을 잡고 실행돼 테스트에서 불러올 수 없습니다. 1단계에서 정책 `checks` 필드를 지웠을 때 서버 상세 화면이 깨졌는데, 브라우저로 직접 열어 보고서야 알았습니다.
- **하드코딩된 데이터:** `'OTHER' → '기타'`, 역할 목록, 결과 표시 이름 같은 값이 공통코드와 별개로 화면·서버 곳곳에 적혀 있습니다. 공통코드에서 이름을 바꿔도 화면 일부에는 반영되지 않습니다.

이 작업이 끝나면 3단계로 CSS(`app.css` 3,824줄)를 정리합니다(별도 설계).

## 2. 목표 / 하지 않을 것 / 실패로 볼 것

**목표**
- 화면마다 **연결부**(DOM 찾기·이벤트·API 호출)와 **로직**(폼 값 만들기·상태 계산·목록 그리기)을 나누고, 로직은 내보내 테스트합니다.
- 화면에 보이는 이름·선택 목록은 **공통코드에서** 가져옵니다.
- 프로그램 동작이 기대는 값은 공통코드로 만들지 않고, 서버와 화면에 중복으로 적힌 것을 **한 곳에서 API로** 내려줍니다.
- 브라우저 테스트로 **모든 화면이 오류 없이 열리는지**와 핵심 흐름을 확인합니다.

**하지 않을 것**
- 화면 기능·배치 변경. 보이는 것과 동작은 그대로입니다. 예외는 공통코드 이름이 반영되는 곳뿐입니다(3.3).
- CSS 정리(3단계).
- 프레임워크나 빌드 도구 도입. ES 모듈을 그대로 브라우저에서 불러옵니다.
- 서버 API 모양 변경. 예외는 3.4에서 추가하는 읽기 전용 정보뿐입니다.

**실패로 볼 것**
- 화면에서 되던 일이 안 됩니다.
- 공통코드에서 이름을 바꿨는데 일부 화면에만 반영됩니다.
- 브라우저 테스트가 Termux에서 돌지 않습니다.

## 3. 결정된 방식

### 3.1 Approaches

| 안 | 내용 | 판단 |
| --- | --- | --- |
| 1 페이지마다 연결부/로직 분리 | 화면별로 순수 함수 모듈을 떼어 fakeDom으로 테스트, 공통 도우미(`codes.js`, `dom.js`) | **채택 (사용자 선택)** |
| 2 공통 컴포넌트 틀 위에 다시 쓰기 | 상태 저장소·다시 그리기 흐름을 만들어 통일 | 테스트 없이 전면 재작성이라 고장을 놓치기 쉬움 |
| 3 구조는 두고 테스트·공통코드화만 | 작업 최소 | "공통 패턴으로 정리" 목적을 못 채움 |

브라우저 테스트는 단위 테스트(fakeDom)와 핵심 흐름 브라우저 테스트를 같이 합니다(사용자 선택). 브라우저 라이브러리는 `puppeteer-core`입니다. `playwright-core`는 Android에서 로드를 거부해 쓸 수 없고, `puppeteer-core`가 Termux의 `chromium-browser`로 동작하는 것을 확인했습니다.

### 3.2 화면 파일 구조

```
src/public/<화면 폴더>/
  <화면>.html
  <화면>.js            연결부: DOM 찾기, 이벤트 연결, API 호출, 아래 모듈 호출 (내보내지 않음)
  <화면>-*.js          로직: 순수 함수 (내보냄, 테스트 대상). 이름은 하는 일로
src/public/shared/js/
  api.js               (그대로) API 호출·오류 알림
  codes.js             공통코드 한 번 불러오기 + 이름·목록 도우미 (새로)
  dom.js               요소 만들기 도우미 el(tag, class, text) 등 (새로, 흩어진 것을 모음)
  status.js            상태 이름 → codes.js 위에서 동작하도록 정리
```

**로직 모듈의 규칙**
- 전역 `document`·`window`에 접근하지 않습니다. 필요한 요소·값은 인자로 받습니다.
- 서버 응답을 받아 화면용 값을 만들거나, 컨테이너 요소를 받아 그 안에 그립니다.
- DOM은 `createElement`와 `textContent`만 씁니다(`innerHTML` 금지, 지금 규칙 유지).

**연결부의 규칙**
- 화면 상태는 파일 맨 위 객체 하나(`const state = {...}`)에 모읍니다. 흩어진 `let` 변수는 없앱니다.

**큰 화면 나누기**
- `server-detail.js`
  - `server-detail.js`: 연결부
  - `server-overview.js`: 기본 정보, 결과 경로, 최근 결과, 이력
  - `server-policy-form.js`: 점검 목록 행 추가·읽기, 저장할 점검 설정 만들기
  - `server-policy-view.js`: 정책 블록·스크립트 선택 그리기
  - `server-script-panel.js`: 스크립트 안내·실행 명령
- `report-detail.js`: 연결부 + `report-sections.js`(섹션별 그리기·요약 문구) + `report-print.js`(인쇄 머리말)
- 나머지 화면(서버 목록, 정책 관리, 스크립트 관리, 공통코드 관리, 변경 이력, 대시보드, 보고서 목록, 결과 수집, 내 정보, 로그인)은 같은 규칙으로 필요한 만큼만 나눕니다. 작은 화면은 로직 모듈 하나로 충분합니다.

### 3.3 공통코드로 옮길 것 (화면에 보이는 이름·선택 목록)

| 하드코딩 | 바꿀 곳 |
| --- | --- |
| `'OTHER' → '기타'` 등 역할 이름 (대시보드, 보고서 목록·상세, 서버 목록·상세) | `serverRoles` 이름 |
| 보고서 목록의 역할 순서 `['WEB','WAS','DB','OTHER']` | `serverRoles` 순서 |
| 보고서 결과 표시 이름 `VIEW_LABELS` | `resultViews` 이름 |
| 상태 이름 기본값(`status.js`) | `healthStatuses` (없을 때만 기본값) |
| 서버 검증의 템플릿 종류·OS·역할 목록(`templates/service.ts`) | `templateKinds`, `operatingSystems`, `serverRoles` |
| 변경 이력 대상 이름 `TARGET_LABELS` | **새 공통코드 분류 `auditTargets`** (seeds에 추가) |

- 공통코드에서 이름을 바꾸면 위 화면에 모두 반영됩니다. 이것이 이 작업의 유일한 "보이는 변화"입니다.
- 서버 검증과 스크립트 관리 화면에 남은 템플릿 종류 `SCRIPT`(통째 스크립트, 대상 역할·제품 입력)는 기본 템플릿에도 공통코드에도 없어 화면에서 고를 수 없는 예전 기능입니다. 검증과 화면의 관련 분기를 지웁니다. (Claude의 판단)

### 3.4 공통코드가 아니라 한 곳으로 모을 것 (프로그램 동작이 기대는 값)

관리자가 바꾸면 스크립트나 DB 제약이 깨지므로 공통코드로 만들지 않습니다.

| 값 | 지금 | 바꿀 곳 |
| --- | --- | --- |
| 정책 분류 `BASIC/WEB/WAS/DB`, 역할 정책 `WEB/WAS/DB` | 서버 여러 파일과 화면에 반복 | 서버: `src/shared/constants.ts` 한 곳. 화면: 공통코드 `policyCategories` 순서로 |
| 점검 만들기 종류·이름, 판정 수준(`Warning`/`Critical`) 이름 | `check-builder-form.js`와 서버 `types.ts`에 중복 | 서버 `GET /api/check-builder/presets` 응답에 종류 목록과 이름을 함께 내려줌 |
| DB 제품별 기본 쿼리 접두어 `DEFAULT_QUERY_PREFIX` | `server-detail.js`와 서버 `db-query-defaults.ts`에 중복 | 서버 점검 설정 응답에 항목별 기본 쿼리 템플릿 id를 넣어 줌 |
| Linux 지원 DB 제품 `LINUX_DB_PRODUCTS` | 서버 한 곳 | 그대로 (화면에서 필요하면 3번째 줄처럼 응답에 포함) |

그대로 두는 것: 표시용 고정값(상태 기호 `○△×－`, 추세 그래프 여백, HTTP 상태 문구, CSP 등).

### 3.5 기준 비교(golden) 파일

공통코드에 `auditTargets`를 더하고(3.3) 점검 설정 응답에 기본 쿼리 템플릿 id를 넣으므로(3.4), `api/common-codes*.json`과 `api/servers/*/check-config.json` 기준 파일이 바뀝니다. 그 작업에서만 기준 파일을 다시 만들고, 바뀐 부분이 추가한 값뿐인지 확인합니다. **생성 스크립트는 바뀌면 안 됩니다.**

### 3.6 테스트

**단위 테스트 (fakeDom, `npm test`에 포함)**
- 새로 떼어 낸 로직 모듈마다 테스트 파일을 둡니다: `test/ui/<화면>-*.test.ts`.
- `test/helpers/fakeDom.ts`는 필요한 만큼만 넓힙니다(예: `querySelector`).
- 1단계 정책 필드 고장 같은 경우는 **서버 응답 → 화면용 값 계산** 함수 테스트로 잡습니다.

**브라우저 테스트 (`npm run test:e2e`, 따로 실행)**
- `puppeteer-core`를 개발 의존성으로 추가합니다.
- 테스트가 임시 폴더에 데모 DB를 만들고(`seedDemo`) 빈 포트로 OpsBox를 띄웁니다.
- 브라우저 경로는 환경 변수 `OPSBOX_E2E_BROWSER`, 없으면 Termux의 `chromium-browser`와 흔한 Chrome 설치 경로를 찾습니다. 없으면 테스트를 건너뜁니다.
- **화면 열기 점검:** 모든 화면 주소(`PAGES`)를 로그인한 상태로 열어 페이지 오류(`pageerror`)와 콘솔 오류가 없는지 확인합니다. 의도된 4xx 응답은 제외합니다.
- **핵심 흐름:**
  - 서버 미사용 → 목록에서 사라짐 → "미사용 포함" → 다시 사용
  - 결과 수집 화면에서 잘못된 경로 거부, 올바른 경로 저장
  - 서버 상세에서 정책 탭 열기 → 정책 저장
  - 공통코드에서 역할 이름 변경 → 보고서 목록에 반영

### 3.7 진행 순서

1. **기반:** 브라우저 테스트 틀과 화면 열기 점검을 먼저 만들어, 지금 상태가 통과하는지 확인합니다(안전망). 그다음 `codes.js`, `dom.js`.
2. **공통코드화(서버):** `auditTargets` 추가, 서버 검증 목록을 공통코드로, `shared/constants.ts`, 점검 만들기·기본 쿼리 정보 API.
3. **화면별 정리:** 작은 화면부터 큰 화면 순서로, 화면마다 로직 모듈 분리 + 하드코딩 제거 + 단위 테스트를 한 커밋씩.
4. **마무리:** 핵심 흐름 브라우저 테스트, 문서(README의 화면 구조·테스트 실행 방법).

각 단계에서 `npm test`, 타입 검사, 기준 비교 테스트, 브라우저 테스트를 모두 통과해야 다음으로 넘어갑니다.

## 4. 구현하는 쪽에 맡기는 것

- 로직 모듈의 정확한 경계와 함수 이름 (3.2의 규칙만 지키면 됨)
- fakeDom을 얼마나 넓힐지
- 화면 열기 점검에서 무시할 콘솔 메시지 목록 (의도된 4xx, favicon 등)
- `codes.js`의 도우미 이름과 모양
