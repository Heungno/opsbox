# CSS 디자인 체계 다시 잡기 설계 (3단계)

작성일: 2026-11-23

## 1. 왜 하는가

화면 모양("점검 일지" 디자인)은 마음에 들지만, CSS 코드는 체계가 없습니다(사용자: "맘에 드는데 체계적으로 바꿔줘").

- `src/public/shared/css/app.css` 3,824줄 한 파일. 앞쪽 약 2,500줄은 예전 GitHub 풍 스타일(`--primary`, `--bg` 등), 2,489줄부터가 지금 보이는 "점검 일지" 층입니다. 뒤 층이 예전 변수를 자기 색에 연결하고 같은 선택자를 다시 정의해 덮어씁니다(선택자 249개가 여러 번 정의됨, `.sidebar`는 8번).
- 값이 제각각: 간격 29종, 글자 크기 18종, 모서리 17종, 직접 적은 색 279종, `!important` 19개, 화면 너비 기준(@media) 480·640·760·768·820·900·1100·1180px.
- 다크 테마가 변수 블록 두 벌과 개별 규칙 17군데에 흩어져 있습니다.
- 인라인 스타일: JS 16곳, HTML 11곳.

목표 상태: 값은 변수(토큰) 한 곳, 다크 테마는 토큰 값만 바꿔서, 규칙은 역할별 파일에 한 번씩. 화면을 고칠 때 어디를 고칠지 바로 알 수 있게.

## 2. 목표 / 하지 않을 것 / 실패로 볼 것

**목표**
- "점검 일지"를 유일한 디자인 체계로. 예전 층은 없앱니다.
- 토큰: 색(용도 이름), 간격 단계, 글자 크기 단계, 모서리, 그림자, 테두리, 화면 너비 기준.
- 다크 테마는 `:root[data-theme="dark"]`에서 **토큰 값만** 바꿉니다. 개별 규칙의 다크 덮어쓰기는 없앱니다(불가피한 예외는 주석과 함께 토큰 블록 옆에 모음).
- 규칙은 역할별 파일에, 선택자는 한 번씩.
- 바꾸기 전·후 스크린샷을 자동으로 비교해 모양이 유지됐는지 확인합니다.

**하지 않을 것**
- 모양 바꾸기. 색·글꼴·배치·사이드바 모양은 지금 그대로입니다.
- 빌드 도구·CSS 프레임워크(Tailwind, Sass, PostCSS 등) 도입. 브라우저가 그대로 읽는 CSS입니다(2단계 원칙).
- 화면 기능·HTML 구조 변경. 예외: 인라인 스타일을 클래스로 옮기는 것, CSS 링크 태그 바꾸기.

**실패로 볼 것**
- 어떤 화면이 눈에 띄게 달라짐(밝은·다크·좁은 화면·인쇄 중 하나라도).
- 다크 테마에서 글자가 안 보이거나 배경이 밝게 남는 곳.
- 정리 후에도 같은 선택자가 여러 파일·여러 곳에 정의되어 덮어쓰는 구조가 남음.
- 브라우저 테스트(화면 열기·흐름·보고서 상세)가 깨짐.

## 3. 결정된 방식

### 3.1 Approaches

| 안 | 내용 | 판단 |
| --- | --- | --- |
| 1 새로 짜고 스크린샷 비교 | 지금 보이는 모양을 기준으로 역할별 파일로 다시 쓰고, 전·후 스크린샷 자동 비교 | **채택 (사용자 선택, 추천)** |
| 2 지금 파일 안에서 고치기 | 중복 합치기, 값→변수, 예전 층 삭제 | 3천 줄 한 파일 구조가 남아 "체계적으로" 목적에 못 미침 |
| 3 Tailwind 등 도구 | 유틸리티 클래스 | 빌드 도구를 들이지 않기로 한 원칙과 충돌, 제외 |

**미세한 차이 허용 (사용자 선택, 추천):** 간격·글자 크기·모서리를 정해진 단계로 맞추면서 생기는 1~2px 차이는 받아들입니다. 7px·15px 같은 값을 그대로 변수로 남기지 않기 위해서입니다. 색은 같은 용도끼리 거의 같은 색(눈으로 구별 안 되는 차이)을 하나로 합칩니다.

### 3.2 파일 구조

```
src/public/shared/css/
  tokens.css       토큰: 글꼴, 색(밝은/다크), 간격, 글자, 모서리, 그림자, 화면 너비 기준 메모
  base.css         초기화, 기본 요소(body, a, 표 기본, 입력 기본, 포커스, 선택 색)
  layout.css       사이드바(계기판 섀시), 본문, 페이지 머리말, 반응형 배치
  components.css   버튼, 카드·패널, 표, 배지·상태 표시, 탭, 입력·폼, 대화상자, 알림, 빈 상태, 명령 상자
  pages/<화면>.css 그 화면에서만 쓰는 규칙 (대시보드, 보고서, 서버, 정책, 스크립트, 공통코드, 결과 수집, 변경 이력, 계정, 로그인)
  app.css          위 파일을 @import 하는 입구 (HTML은 지금처럼 app.css 하나만 링크)
src/public/reports/report-print.css   인쇄용. 파일 위치·링크는 그대로 (3.2.1)
```

- HTML은 계속 `app.css` 하나만 링크합니다. 캐시 버전 표시(`?v=`)는 전 화면 같은 값으로 바꿉니다.
- `@import` 순서: tokens → base → layout → components → pages. 뒤 파일이 앞 파일 선택자를 다시 정의하지 않습니다(화면 파일은 그 화면 전용 클래스만).

### 3.2.1 인쇄 CSS (Claude의 판단)

`report-print.css`는 보고서 상세에만 따로 링크되는 **인쇄 층**으로 둡니다. 공문서 형식(검정 글자, 바탕체, 흰 종이)이라 화면 토큰과 다른 값이 필요하고, `@media print` 안에서 공통 선택자(`body`, `.card`, `table` 등)를 덮어쓰는 것이 이 파일의 목적입니다.
- 파일 맨 위에 인쇄용 토큰 블록(`--print-ink`, `--print-rule`, `--print-font` 등)을 두고, 규칙 안에서는 그 토큰만 씁니다.
- 다크 테마로 인쇄해도 흰 종이에 검정 글자가 나오게, 인쇄 토큰 블록에서 다크 값을 덮어쓰는 것은 허용합니다.
- 3.7 검사에서 이 파일은 "인쇄 층"으로 따로 취급합니다: 직접 색은 인쇄 토큰 블록에만, 공통 선택자 재정의는 `@media print` 안에서만 허용. `app.css`에서 불러와야 한다는 검사에서는 빠집니다.

### 3.3 토큰 규칙

- **색은 용도 이름**으로: 바탕(`--paper`), 표면(`--surface`, `--surface-sunk`), 글자(`--ink`, `--slate`, `--slate-soft`), 선(`--rule`, `--rule-soft`), 강조(`--petrol` 계열), 상태(`--ok`, `--warn`, `--crit`, `--idle`)와 그 옅은 배경, 사이드바(`--chassis` 계열), 코드 강조 색. 지금 "점검 일지" 블록의 이름을 기본으로 씁니다.
- 예전 별칭(`--primary`, `--bg`, `--text-light` 등)은 없애고 사용처를 새 이름으로 바꿉니다.
- 규칙 안에는 직접 적은 색이 없어야 합니다(`transparent`, `currentColor`, `color-mix()`로 토큰 섞기는 허용).
- **간격**: 4px 기준 단계(예: 2·4·8·12·16·20·24·32·40·56). 단계 수와 이름은 구현자 판단.
- **글자 크기**: 지금 쓰는 크기들을 6~8단계로 묶음.
- **모서리**: 지금 `--radius-panel`(10px), `--radius-control`(6px)에 작은 것·둥근 것(999px) 정도. `50%`(원)은 그대로 허용.
- **화면 너비 기준**: CSS 변수는 @media 안에서 못 쓰므로, 몇 개의 기준(예: 480·640·900·1180)으로 합치고 tokens.css에 주석으로 목록을 둡니다. 기준을 옮기면 중간 너비(태블릿·분할 화면)의 배치가 바뀔 수 있으므로, 스크린샷은 768·1024px 너비도 찍고(3.5), 합친 뒤 그 너비에서 배치가 달라지면 그 기준은 합치지 않고 남깁니다. (Claude의 판단)
- `!important`는 없앱니다. 꼭 필요하면(예: `[hidden]` 강제) 이유를 주석으로.

### 3.4 인라인 스타일

- 고정 값인 인라인 스타일(예: `server-detail.js`의 체크박스 크기 `cssText`, HTML의 `style="..."`)은 클래스로 옮깁니다.
- 계산 값(대시보드 상태 막대 `flexGrow`, 그래프 위치·너비 등)은 그대로 둡니다.

### 3.5 모양 확인: 스크린샷 비교

- **기준 찍기가 첫 작업**입니다. 정리 시작 전에 지금 모양을 찍어 둡니다.
- 2단계 브라우저 테스트 틀(`test/e2e/helpers`, puppeteer-core, 임시 데모 DB)을 그대로 씁니다. 데모 데이터의 날짜·시각처럼 매번 바뀌는 글자는 가리거나 고정합니다.
- **찍을 것**: 모든 화면(`PAGES`) × 밝은/다크 × 너비 1440·1024·768·390px. 그 외 상태: 서버 상세의 정책·스크립트 탭, 서버 수정 대화상자, 사이드바 접힘, 보고서 상세 인쇄(인쇄 모드 흉내), 로그인 화면.
- **비교는 두 종류로 나눕니다 (Claude의 판단).** 단계 맞춤(1~2px)은 긴 표·목록에서 아래로 갈수록 쌓이고 줄바꿈도 바꿔서, 구조 정리와 섞으면 거의 모든 화면이 차이 나 회귀를 가려낼 수 없습니다.
  - **구조 정리 단계**(3.6의 2~6): 값은 지금 그대로(토큰 값 = 지금 값) 두고 파일·선택자·다크 처리만 바꿉니다. 원래 스크린샷과 **거의 같아야** 통과합니다(글꼴 안티앨리어싱 정도의 차이만 허용).
  - **단계 맞춤 단계**(3.6의 7): 그다음 토큰 값을 정해진 단계로 맞춥니다. 이 단계의 차이는 전·후를 나란히 보여 주는 비교 페이지로 만들어, Claude가 화면마다 "단계 맞춤으로 인한 밀림·줄바꿈"인지 "깨짐"인지 확인하고, 마지막에 **사용자가 비교 페이지를 한 번 보고** 병합을 정합니다.
- 기준 스크린샷과 차이 이미지는 저장소에 넣지 않습니다(용량, Termux와 PC의 글꼴 렌더링 차이). 작업 중 비교용입니다.
- 비교 스크립트는 `npm run test:visual` 같은 이름으로 남겨 나중에도 쓸 수 있게 합니다(기준 다시 찍기 명령 포함).

### 3.6 진행 순서

1. 스크린샷 기준 찍기 + 비교 도구.
2. `tokens.css`: "점검 일지" 토큰 정리, 지금 쓰는 값을 그대로 토큰으로, 다크 테마 값 모으기.
3. `base.css`, `layout.css` (사이드바·본문) → 엄격 비교.
4. `components.css` → 엄격 비교.
5. 화면별 파일 (작은 화면부터) → 화면마다 엄격 비교.
6. 인쇄 CSS, 인라인 스타일, 예전 `app.css` 내용 삭제(입구 파일만 남김), 3.7 검사 → 엄격 비교.
7. 단계 맞춤: 간격·글자 크기·모서리·너비 기준을 단계로, 비슷한 색 합치기 → 전·후 비교 페이지.
8. 문서.

각 단계에서 `npm test`, 브라우저 테스트(`npm run test:e2e`), 스크린샷 비교(2~6은 엄격, 7은 확인)를 통과해야 다음으로 넘어갑니다. 이 순서 동안 예전 `app.css`와 새 파일이 함께 있는 기간이 있으므로, 옮긴 규칙은 예전 파일에서 바로 지웁니다.

### 3.7 검사 (자동)

정리 결과를 숫자로 확인하는 작은 검사를 테스트로 둡니다.
- 토큰 파일 밖의 직접 색 0개.
- 같은 선택자가 두 파일 이상에 정의된 경우 0개 (같은 파일 안 @media 안의 재정의는 허용).
- `!important`는 주석 단 것만.
- 모든 CSS 파일이 `app.css`에서 불러와짐.

### 3.8 문서

- README "화면 코드 규칙"에 CSS 규칙 추가: 파일 역할, 토큰만 쓰기, 다크는 토큰으로, 새 화면 CSS는 `pages/`.
- `tokens.css` 맨 위에 토큰 목록과 쓰임새 주석.

## 4. 구현하는 쪽에 맡기는 것

- 간격·글자 크기 단계의 정확한 값과 이름, 컴포넌트 묶음 경계.
- 같은 용도로 합칠 색 판단(눈으로 구별 안 되는 차이).
- 스크린샷 차이 계산 방법(브라우저 캔버스로 비교하거나 개발 의존성 추가)과 차이 기준값.
- 화면 파일을 더 나눌지 합칠지.
- 매번 바뀌는 글자를 가리는 방법.
