# 점검 만들기 (Check Builder) 설계

작성일: 2026-11-21

## 1. 목적과 배경

스크립트(PowerShell·bash)를 모르는 운영 담당자도 OpsBox 화면에서 새 점검 항목을 만들 수 있게 한다.

지금 기본 제공 항목(CPU·메모리·디스크·프로세스·포트·HTTP, WEB·WAS·DB 역할 항목)이 아닌 점검을 추가하려면:

1. **점검 정책 관리**에서 항목(ID·이름·실행 방식·결과 표시)을 추가하고
2. **스크립트 관리**에서 같은 항목 ID로 스크립트 조각을 직접 작성해, 내부 결과 구조
   (`$rolePolicyResults += @{ role = 'BASIC'; item = …; status = … }`)에 맞춰 결과를 남겨야 한다.

2단계가 스크립트를 모르는 사람이 막히는 지점이다. 또한 **Linux는 사용자 항목을 아예 수집하지 않는다**
(`LINUX-PART-SAVE`가 정책 정의만 `policyItems`로 넘겨 보고서에 항상 미수집으로 나옴).

기준 자료는 `doc/INFORMATION_SYSTEM_PREVENTIVE_CHECK_MANUAL.md`(정보시스템 예방점검 매뉴얼)이다.
매뉴얼에서 아직 자동화되지 않은 항목 대부분이 아래 6가지 유형으로 묶인다.

## 2. 목표 · 비목표 · 반목표

**목표**
- 정책 관리의 항목 추가 창에서 **실행 방식 "점검 만들기"** 를 고르면 안내형 폼이 나오고, 폼만 채우면 점검 항목이 완성된다.
- 6가지 유형을 지원한다.
  1. 명령 결과 숫자 비교
  2. 명령 결과 문구 확인
  3. 설정값 비교 (Linux 커널 파라미터 / Windows 레지스트리 값)
  4. 원격 포트 접속
  5. 파일 최신 여부
  6. 로그 문구 검색
- 명령이 필요한 유형(1·2·3)은 **준비된 점검 목록**에서 고르면 OS에 맞는 명령과 기본 기준값이 채워진다. 목록에 없으면 **직접 입력**도 허용한다.
- 서버마다 다른 값(대상 주소, 파일 경로 등)은 **서버 상세**에서 입력한다(기존 `scope: SERVER` 입력 방식 재사용).
- 결과는 다른 항목처럼 보고서에 상태(정상·주의·위험·미수집)와 표로 나온다.
- Linux에서도 사용자 항목(점검 만들기 항목과, 사용자가 직접 쓴 스크립트 항목 모두)이 수집된다.

**비목표**
- 6가지 유형 밖의 점검(이런 점검은 지금처럼 스크립트를 직접 작성).
- 한 항목으로 Windows·Linux를 동시에 지원(정책이 OS별이므로 항목도 그 정책의 OS 전용).
- 원격 실행·에이전트·스케줄링(점검 스크립트 실행 방식은 그대로).
- 사용자 권한 구분(별도 과제. 아래 제약 참고).

**반목표 (기술적으로 동작해도 실패로 보는 것)**
- 폼에 입력한 값(직접 입력 명령 제외)이 셸·PowerShell 코드로 해석되어 실행되는 것.
- 기존 사용자 템플릿·정책 항목·점검 결과가 깨지거나 바뀌는 것.
- 생성된 Windows 스크립트가 PowerShell 3.0(Windows Server 2012)에서 동작하지 않는 것.
- 사용자가 직접 고친 생성 조각을 폼 저장이 덮어써 수정 내용이 사라지는 것.

## 3. 제약

- **지원 범위**: Windows Server 2012 이상·PowerShell 3.0 이상, Linux bash 4.2 이상(README 지원 범위). 생성 코드도
  `::new()`, `-in`, `class`, `using` 를 쓰지 않는다(`test/builtInUpgrade.test.ts`의 문법 검사와 같은 규칙).
- **실행 권한**: 점검 스크립트는 보통 관리자(root)로 실행된다. 직접 입력 명령은 그 권한으로 그대로 실행되므로,
  현재처럼 로그인한 누구나 정책을 고칠 수 있는 상태에서는 위험이 크다. 이 기능을 쓰는 사람이 늘수록 권한 구분
  (관리자/일반) 과제의 우선순위가 올라간다. 이번 범위에서는 직접 입력 명령을 저장할 때 경고 문구를 보여 주고,
  감사 로그(정책 수정)에 명령 내용이 남는 것으로 대신한다.
- **오프라인**: 외부 CDN·라이브러리 없이 동작(기존 화면 원칙).
- **CSP**: 화면에 인라인 스크립트·`onclick` 금지(`script-src 'self'`).
- **검증 환경**: 개발 환경(Termux)에 PowerShell이 없다. Windows 생성 코드는 정적 검사와 리뷰로 확인하고,
  가능하면 Windows에서 한 번 실제 실행한다(아래 9장).

## 4. 검토한 방식 (Approaches)

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| 1. 공통 실행기 + 데이터 | OS별 실행기 조각 하나가 설정 데이터로 받은 항목 정의를 유형별로 실행 (DB 쿼리 실행기와 같은 구조) | 입력값이 코드가 되지 않음, 실행기 수정이 전체에 반영 | 초기 작업량 큼, 생성 결과를 사람이 읽고 고칠 수 없음 |
| **2. 폼에서 스크립트 조각 생성 (선택)** | 폼을 저장하면 OpsBox가 항목 전용 PowerShell/bash 조각을 만들어 템플릿으로 저장, 기존 조립 경로로 들어감 | 생성된 스크립트를 보고 직접 고칠 수 있음(배우는 교재, 막다른 길 없음), 기존 템플릿·조립 구조 그대로 | 값을 코드에 넣으므로 따옴표 처리 실수가 곧 보안 문제, 항목마다 조각이 쌓임, 생성기 개선이 기존 항목에 자동 반영되지 않음 |
| 3. 방식 1 + 스크립트로 바꾸기 | 방식 1에 "편집 가능한 스크립트로 바꾸기" 버튼 추가 | 1의 안전성 + 막다른 길 없음 | 범위가 가장 큼 |

**사용자 선택: 방식 2.** 방식 2의 단점은 다음으로 줄인다.
- 값 삽입은 **OS별 단일 인용 함수**만 거친다(5.4).
- **서버별 값은 코드에 넣지 않고** 실행 중에 설정(config)에서 읽는다. 코드에 들어가는 것은 정책 단위 값(유형, 준비된 점검 ID, 명령, 기준값)뿐이다.
- 생성기 개선 반영: 생성 조각에 **생성기 버전**을 기록하고, 고치지 않은(직접 편집되지 않은) 조각은 업그레이드 시 다시 생성한다(기존 `BUILTIN_TEMPLATE_UPGRADES`와 같은 생각).

## 5. 설계

### 5.1 데이터 모델

**정책 항목** (`PolicyItem`, 기존 구조에 값만 추가)

```jsonc
{
  "id": "CUSTOM_3F2A…",            // 기존 규칙 그대로 (CUSTOM_ + 16자리)
  "name": "Swap 사용률",
  "enabled": true,
  "executor": {
    "type": "CHECK_BUILDER",       // 새 실행 방식 (공통코드 policyExecutors에 추가, 표시명 "점검 만들기")
    "templateId": "GEN-CUSTOM_3F2A…-LINUX",  // 생성된 조각
    "options": {
      "builder": {
        "version": 1,              // 폼 데이터 형식 버전
        "type": "COMMAND_NUMBER",  // COMMAND_NUMBER | COMMAND_TEXT | SETTING_VALUE | REMOTE_PORT | FILE_FRESHNESS | LOG_PATTERN
        "presetId": "linux.swap",  // 준비된 점검 ID, 직접 입력이면 null
        "command": "…",            // 직접 입력일 때만 (준비된 점검은 프리셋에서 가져옴)
        "...": "유형별 값 (5.2)"
      }
    }
  },
  "inputs": [ /* 서버별 입력 (scope: SERVER) — 유형·프리셋이 정함 */ ],
  "result": { "components": [{ "type": "SUMMARY" }, { "type": "TABLE", "columns": [ … ] }], "statusField": "status" }
}
```

**생성된 템플릿** (`ManagedTemplate`에 선택 필드 추가)

```jsonc
{
  "id": "GEN-CUSTOM_3F2A…-LINUX",
  "kind": "SCRIPT_PART", "os": "Linux", "item": "CUSTOM_3F2A…", "enabled": true,
  "name": "점검 만들기 · Swap 사용률",
  "content": "…생성된 bash…",
  "generated": {
    "by": "CHECK_BUILDER",
    "generatorVersion": 1,
    "itemId": "CUSTOM_3F2A…",
    "contentSha256": "…"           // 생성 당시 내용. 지금 내용과 다르면 '직접 편집됨'
  }
}
```

- "직접 편집됨"은 별도 플래그 대신 `contentSha256`과 현재 내용 비교로 판단한다(스크립트 관리에서 저장해도 별도 처리 불필요).
- 직접 편집된 조각은 폼 저장·업그레이드가 덮어쓰지 않는다. 폼에는 "이 항목의 스크립트는 직접 편집되었습니다. 폼 변경은 스크립트에 반영되지 않습니다. [폼 기준으로 다시 만들기]"를 보여 준다(다시 만들기는 확인 후 덮어씀, 이전 내용은 템플릿 이력에 남음).
- 항목을 삭제하면 생성 템플릿도 삭제한다. 단, 직접 편집된 경우 확인을 받는다.

### 5.2 유형별 폼과 판정

모든 유형 공통: 명령이 없거나(`command not found`) 대상이 없으면 **미수집**, 실행 시간 초과(30초)는 **미수집**과 메시지.

| 유형 | 정책 단위 값 (폼) | 서버별 값 (서버 상세) | 판정 |
|---|---|---|---|
| 1. 명령 결과 숫자 비교 `COMMAND_NUMBER` | 준비된 점검 또는 명령, 단위(표시용), 방향(높을수록 나쁨/낮을수록 나쁨), 주의·위험 기준 | 프리셋이 정한 값(예: Ping 대상) | 출력의 첫 숫자를 값으로 읽어 기준 비교. 숫자가 없으면 미수집 |
| 2. 명령 결과 문구 확인 `COMMAND_TEXT` | 준비된 점검 또는 명령, 비정상 문구(하나 이상), 정상 문구(선택), 비정상일 때 수준(주의/위험) | 프리셋이 정한 값 | 비정상 문구가 있으면 지정 수준, 정상 문구를 지정했는데 없으면 주의, 아니면 정상. 대소문자 무시, 단순 포함(정규식 아님) |
| 3. 설정값 비교 `SETTING_VALUE` | 준비된 점검 또는 설정 이름(Linux: sysctl 키, Windows: 레지스트리 경로+값 이름), 비교(=, ≠, ≥, ≤), 기대값, 불일치 수준 | 없음 | 읽은 값과 기대값 비교. 숫자 비교는 둘 다 숫자일 때만 |
| 4. 원격 포트 접속 `REMOTE_PORT` | 접속 제한 시간(초, 기본 3), 실패 수준(기본 위험) | 대상 목록(`호스트:포트`, 여러 개) | 대상별 접속 성공/실패, 항목 상태는 최악 |
| 5. 파일 최신 여부 `FILE_FRESHNESS` | 허용 기간(시간), 파일이 없을 때 수준(기본 위험) | 파일 경로 목록 | 마지막 수정 시각이 허용 기간보다 오래되면 주의, 없으면 지정 수준 |
| 6. 로그 문구 검색 `LOG_PATTERN` | 찾을 문구(여러 개), 검색 기간(일), 주의·위험 건수 기준 | 로그 파일·폴더 경로 목록 | 기간 안의 줄 중 문구 포함 줄 수를 기준 비교. 표본 5줄 표시 |

결과 표 열(공통): 대상, 값, 기준, 상태, 메시지. 명령 유형은 출력 일부(최대 2,000자)를 메시지에 담는다.

### 5.3 준비된 점검 목록 (프리셋)

`src/services/checkBuilder/presets.ts`(가칭)에 코드로 둔다(공통코드로 사용자가 고치게 하지 않음: 명령이므로).
각 프리셋: `id`, `os`, `type`, `name`, `description`, `command`(또는 설정 이름), 기본 기준값, 서버별 입력 정의.
매뉴얼 항목 기준 1차 목록(명령은 구현 시 실제 환경에서 확인):

| 매뉴얼 항목 | Linux | Windows |
|---|---|---|
| Swap / Paging 사용률 | `free` 의 Swap 사용률 (숫자, 50/80) | `Win32_PageFileUsage` 사용률 (숫자, 50/80) |
| I-Node 사용률 | `df -Pi` 최대 IUse% (숫자, 70/90) | — (해당 없음) |
| Ping 손실 | `ping -c 5` 손실률, 대상 미입력 시 기본 게이트웨이 (숫자, 20/60) | `Test-Connection -Count 5` 손실률 (숫자, 20/60) |
| NIC 링크 상태 | `ip -o link` 의 `state DOWN` (문구, 위험) | `Get-NetAdapter` 물리 NIC 중 Up 아님 (문구, 위험) |
| Disk 이중화 | `/proc/mdstat` 의 결손 표시 `_` (문구, 위험) | `Get-PhysicalDisk` HealthStatus ≠ Healthy (문구, 위험) |
| Multipath 이중화 | `multipath -ll` 의 `failed`·`faulty`·`offline` (문구, 위험) | `mpclaim -s -d` 실패 경로 (문구, 위험) |
| HBA 연결 | `/sys/class/fc_host/*/port_state` ≠ Online (문구, 위험) | `Get-InitiatorPort` 연결 상태 (문구, 위험) |
| Cluster 데몬 | `pcs status` 의 `OFFLINE`·`Stopped`·`FAILED` (문구, 위험) | `Get-ClusterNode` State ≠ Up (문구, 위험) |
| Kernel Parameter | `sysctl -n <키>` (설정값) — 키·기대값 사용자 지정 | 레지스트리 값 (설정값) — 경로·이름·기대값 사용자 지정 |

명령이 없는 서버(예: multipath 미사용)는 미수집으로 남는다. 프리셋 명령은 읽기 전용 조회만 사용한다.

### 5.4 스크립트 생성

`src/services/checkBuilder/` (가칭)
- `generateWindows(item, preset)` / `generateLinux(item, preset)` → 조각 문자열.
- **값 삽입은 한 함수만**: Windows `psLiteral(value)` = `[Text.Encoding]::UTF8.GetString([Convert]::FromBase64String('<base64>'))`,
  Linux `shLiteral(value)` = 작은따옴표 인용(`'` → `'\''`, 기존 `linuxScriptService.quote`와 같은 방식). 숫자 기준값도 문자열로 넣고 실행 중 숫자 변환.
- **서버별 값은 코드에 넣지 않는다.** Windows는 `$opsboxConfig.checks.rolePolicySettings.<항목ID>.inputs`에서 읽는다.
  Linux는 설정 전달에 일반 통로를 추가한다: 사용자 항목 입력을 JSON 한 덩어리(`OPSBOX_ITEM_INPUTS_JSON`)로 넘기거나
  항목·키별 배열로 넘긴다(구현 시 기존 `scalar`/`array` 방식 중 jq 없이 bash로 읽기 쉬운 쪽을 고른다. bash에서 JSON 파싱은 피하는 편이 낫다).
- 생성 조각은 기존 결과 경로로 결과를 남긴다.
  - Windows: `$rolePolicyResults += @{ role = '<BASIC|WEB|WAS>'; item = '<ID>'; status = …; detail = @{ rows = @(…); … } }` (SAVE 조각이 이미 처리).
  - Linux: 새로 정의하는 공통 함수(예: `opsbox_record_item ROLE ITEM STATUS DETAIL_JSON`)로 남기고, `LINUX-PART-SAVE`가 이를 `policyItems`/`rolePolicies`에 반영(현재 미수집 문제 해결). 직접 작성한 사용자 스크립트도 이 함수를 쓰면 수집되도록 문서화.
- 생성 코드는 단계 로그(`Write-OpsBoxLog` / `opsbox_log`)를 남기고, 예외는 잡아서 미수집으로 기록(스크립트 전체가 멈추지 않게).
- 명령 실행은 시간 제한(30초)을 둔다. Windows는 기존 WebtoB 조각처럼 프로세스 실행+대기, Linux는 `timeout` 이 있으면 사용.

### 5.5 화면

**점검 정책 관리 › 항목 추가/편집 창**
- 실행 방식에 "점검 만들기" 추가. 선택 시 기존 템플릿 선택·JSON 입력칸을 숨기고 안내형 폼 표시.
- 흐름: 점검 유형 → 준비된 점검(유형 1·2·3) 또는 직접 입력 → 유형별 값 → 항목 이름(프리셋 이름으로 자동 채움) → [생성될 스크립트 보기] → 저장.
- 프리셋을 고르면 설명, 실행 명령(읽기 전용 미리보기), 기본 기준값, 서버별 입력 안내를 보여 준다.
- 직접 입력 선택 시 경고: "입력한 명령은 점검 스크립트 실행 계정(보통 관리자) 권한으로 그대로 실행됩니다."
- [생성될 스크립트 보기]: 저장 전 생성 결과를 구문 강조로 보여 준다(기존 syntax-highlight 재사용).
- 저장 시 정책 저장과 함께 생성 템플릿 생성/갱신(서버 API에서 한 번에, 감사 로그는 정책 수정 1건 + 템플릿 변경 이력).

```
┌ 점검 항목 추가 ─────────────────────────────┐
│ 실행 방식   [점검 만들기 ▼]                  │
│ 점검 유형   [명령 결과 숫자 비교 ▼]          │
│ 준비된 점검 [Swap 사용률 ▼]  (직접 입력 …)   │
│   └ 실행 명령(미리보기): free | awk …        │
│ 기준값      주의 [ 70 ] %  위험 [ 90 ] %     │
│ 항목 이름   [Swap 사용률                ]    │
│                    [생성될 스크립트 보기] [저장] │
└────────────────────────────────────────────┘
```

**서버 상세** — 변경 없음에 가깝다. 정책 항목의 `scope: SERVER` 입력이 기존 `appendBasicPolicyInputs`로 표시된다.
입력 형식이 부족하면(예: `호스트:포트` 목록) `PolicyInputType`에 `TARGET_LIST` 정도를 추가한다.

**스크립트 관리** — 생성 템플릿에 "자동 생성"(직접 편집 시 "직접 편집됨") 표시와 연결된 정책 항목 링크.

**보고서** — 새 화면 없음. 기존 정책 항목 결과 표시(SUMMARY + TABLE)를 그대로 쓴다. WEB·WAS·DB 정책에 넣은 항목도 같은 방식.

### 5.5.1 사용할 수 있는 정책 유형

기본(BASIC), WEB, WAS, **DB** 정책 모두에서 쓸 수 있다(사용자 결정). DB 정책은 매뉴얼의 리스너 프로세스 기동,
DB·리스너 로그, 환경 설정 파일 백업처럼 쿼리가 아닌 DBMS 항목을 담기 위해 허용한다. 이에 따라:
- `savePolicy`의 "DB 정책은 SQL_QUERY만" 규칙을 "SQL_QUERY 또는 CHECK_BUILDER"로 바꾼다(다른 정책의 SQL_QUERY 금지는 유지).
- 스크립트 조립(`selectScriptParts`): 지금 DB 역할은 `DB_QUERY_RUNNER` 하나만 넣는다. DB 역할 항목 중 SQL 항목이 있으면
  `DB_QUERY_RUNNER`를, CHECK_BUILDER 항목은 각자의 생성 조각을 넣는다. 둘 다 있으면 둘 다.
- DB 쿼리 실행기 설정(`policyQueries`·`rolePolicySettings`의 쿼리 대상)은 SQL 항목만 받도록 걸러, 실행기가
  CHECK_BUILDER 항목을 쿼리로 실행하려 하지 않게 한다. 서버 저장 검증의 'DBMS와 맞는 쿼리 템플릿을 선택하세요'도 SQL 항목에만 적용.
- 결과는 `rolePolicies.DB.items`에 들어가 기존 DB 항목과 같은 목록에 보인다.

### 5.6 서버 API · 검증

- 정책 저장(`savePolicy`)에서 `CHECK_BUILDER` 항목 검증: 유형·프리셋 존재, OS 일치, 기준값 숫자·순서(주의 < 위험, 방향 고려), 문구 비어 있지 않음, 길이 제한(명령 2,000자, 문구 200자 × 20개).
- 정책 저장 시 생성 템플릿을 같은 트랜잭션으로 생성/갱신/삭제.
- 정책 항목 ID ↔ 생성 템플릿 연결은 `executor.templateId` + `generated.itemId` 양쪽.
- 템플릿 저장(`saveTemplate`)은 지금 입력에 없는 필드를 버린다. 기존 레코드의 `generated`를 **그대로 보존**하고,
  클라이언트가 보낸 `generated`는 무시한다(가짜 '자동 생성' 표시 방지). 이렇게 해야 스크립트 관리에서 고쳐 저장한 뒤에도
  해시 비교로 '직접 편집됨'을 판단할 수 있다.
- 스크립트 관리에서 정책 항목에 연결된 생성 템플릿은 삭제할 수 없다(409, "점검 정책 관리에서 항목을 삭제하세요").
  지우면 스크립트 조립 시 템플릿 없음 오류가 나기 때문.

### 5.7 업그레이드

- `generatorVersion`이 오른 경우, 고치지 않은 생성 템플릿(`contentSha256` 일치)은 앱 시작 시 다시 생성(`applyBuiltInUpdates`에 추가).
- 공통코드는 DB를 처음 만들 때만 `data/common-codes.json`에서 들어간다(`settings.common_codes`). 따라서 기존 DB에는
  `policyExecutors`에 `CHECK_BUILDER`가 없다. `applyBuiltInUpdates`에 빠진 실행 방식 코드를 채우는 단계를 추가한다
  (사용자가 지운 코드를 되살리지 않도록 기존 정책 항목 추가 마이그레이션처럼 1회 기록).
- 기존 사용자 항목(직접 작성 스크립트)은 손대지 않는다. Linux SAVE 변경은 기본 조각 업그레이드(`BUILTIN_TEMPLATE_UPGRADES`)로 반영.

- 방식 2(폼에서 스크립트 조각 생성).
- 6가지 유형 그대로.

## 7. 제가 정한 것 (검토 부탁)

- 항목은 그 정책의 OS용 조각 하나만 생성(정책이 OS별이므로).
- 값 삽입은 OS별 단일 인용 함수만 사용, 서버별 값은 코드에 넣지 않고 실행 중 설정에서 읽음.
- "직접 편집됨"은 생성 당시 내용 해시와 비교해 판단, 직접 편집된 조각은 덮어쓰지 않음(확인 후 다시 만들기 가능).
- 프리셋은 사용자가 고칠 수 있는 공통코드가 아니라 코드에 둠.
- 문구 확인은 정규식이 아닌 단순 포함(대소문자 무시) — 비전문가가 정규식 특수문자로 실수하지 않게.
- 명령 실행 시간 제한 30초, 출력은 최대 2,000자 보관.
- 직접 입력 명령은 경고 문구 + 감사 로그로 대신하고, 권한 구분은 별도 과제로 둠.

## 8. 구현자에게 맡기는 것

- 폼 레이아웃 세부(기존 모달 스타일 따름).
- 파일·폴더 이름(`checkBuilder/` 등)과 모듈 경계.

## 9. 검증

- **Linux**: 생성 조각을 실제 bash로 실행하는 테스트(기존 `linuxDbScript.test.ts`처럼 가짜 명령 사용). 유형 6가지 × 정상·주의·위험·미수집, 따옴표·`$(…)`·역슬래시가 든 입력이 실행되지 않는지, 결과가 `policyItems`/`rolePolicies`에 들어가는지.
- **Windows**: PowerShell이 없으므로 정적 테스트 — 값이 모두 base64 인용 함수를 거치는지, PS 5 전용 문법이 없는지, 생성 결과 스냅샷. 가능하면 Windows Server(PS 5.1)에서 데모 정책으로 1회 실제 실행.
- **업그레이드**: 기존 DB(사용자 항목·직접 작성 템플릿 포함)에서 앱 시작 후 변화 없음, 생성 템플릿 재생성·직접 편집 보존.
- **데모 데이터**: `npm run demo:seed`에 점검 만들기 항목 2~3개(예: Swap 사용률, 원격 포트 접속) 결과를 추가해 화면 확인.
